# 揭棋 AI 优化说明

> 本文说明这次把 `Game/` 里的 AI 从「1 层贪心启发式」换成「正确的揭棋规则引擎 +
> 不完全信息搜索」的全过程：旧代码有什么问题、新引擎怎么工作、怎么配置、怎么验证。

---

## 1. 一句话总结

| | 旧版 | 新版 |
|---|---|---|
| 搜索 | 名义「深度 1」，实际只做一步静态打分 | 迭代加深 Negamax / Alpha-Beta(PVS) + 置换表 + 杀手着法 + 历史启发 + 静态搜索 + 空着裁剪 + 将军延伸；局面分按 Zobrist 缓存 |
| 规则 | 士/象走法与引擎不一致，且**会选择违规着法** | 位棋盘规则引擎，与 GUI 走法验证器逐格比对一致；"送将"类着法有专门的差分测试守着 |
| 暗子 | 读取暗子真实身份参与评估（等于作弊） | **结构上不可能**读取暗子身份；用后验期望 + 采样搜索 |
| 每步输出 | 283 行调试打印 | 2~3 行摘要（`verbose` 可看详细） |
| 每步耗时 | ~0.5 秒 | 默认 2 秒（可配），开局 2 秒能到 4 层、约 5 万节点 |
| 界面 | 只有棋盘，看不到走棋记录/评估/点评 | 三区布局（深色卡片风）：顶部配置区 + 棋盘 + 右侧信息面板；排版全部走统一间距/圆角令牌 |
| 棋盘信息 | 只有棋子 | 外围坐标（汉字/数字随视角翻转）、上一步四角标记、选中流光、**可走点小圆点**（吃子画空心圈）、**上下两条被吃棋子展示条** |
| 复盘 | 只能整体回退，点评丢失 | **步数自由前进/后退**（开局/上一步/下一步/最新）、**点评按步数存档**、**「回顾棋局」浮层**（大棋盘 + 双方被吃之子摘要）、**分支树**（复盘变招：变招里还能再变招，来回切换都不丢招） |
| 棋谱 | 无 | **下完自动存 `Game/records/*.json + *.txt`**；`record_tool.py` 支持列表/查看/复盘找失着/导出训练样本 |
| 大模型 | 无 | 只点评（默认）/ 影响选着 / **直接采用它的招法**（顶部可开关）；点评带上走棋记录、评估走势、上一次点评，且**只点评 AI 自己的招法**；**归属事实表 + 点评质检**（见 §8.4） |
| 线程 | 在子线程里直接改棋盘，与渲染抢动画列表 | 子线程只算，主线程落子 |
| 可测性 | 无 | 477 个单元测试 + 自对弈 / 界面预览 / 合法性审计 / 引擎体检 / 棋谱工具 |

## 2. 旧 AI 到底哪里不对（都有可复现证据）

1. **会走违规着法（最严重）**
   `AI.py` 的根节点选着用的是 `game_score()`，而排序用的是
   `calculate_piece_move()`——两套评分标准。`game_score()` 对被将军只扣
   `check_punish = 15` 分，于是「不应对将军而去吃子」的着法反而得分更高。

   实测（开发工作区里的 `tools/legacy_diagnosis.py`，红方被黑车将军的局面）：
   ```
   着法                    排序分          最终评估分   合法
   (0,4)->(1,4)                56              73     是
   (5,0)->(5,4)         -99999943              48     否
   (5,0)->(5,3)         -99999984             675     否   <- 旧 AI 选了这一手
   ```
   旧 AI 其实**知道**这手棋违规（排序分 -1 亿），但它最终取舍用的是另一套
   `game_score()`，那里"被将军"只值 15 分，于是违规着法反而胜出。
   而 `main.py` 应用 AI 着法时不做任何校验，所以这些违规着法会真的落到棋盘上。
   自对弈里旧 AI 的每一局都因为走违规着法而告负。

2. **暗子真值泄漏**：`game_score()` / `_check_check()` 直接用
   `piece['actual']`，AI 知道对方（甚至自己）暗子是什么，对人类不公平。

3. **规则不一致**：`config.validate_advisor()` 把暗士限制成「只有四个角进中心」，
   而明士又完全没有九宫限制；`validate_elephant()` 没有过河限制。
   见第 4 节，正确规则是「明士明象可以过河」。

4. **性能**：`game_state.is_checkmate()` 对每个子、每个目标格都做一次
   `deepcopy` 再全盘扫描，每走一步都要跑一次，界面因此明显卡顿。

5. **重复局面判定**依赖 `hash(str)`（进程内随机）且把暗子真值写进哈希。

6. 子线程里直接 `move_piece()`，与主线程渲染抢 `gs.animations`，是竞态。

## 3. 新引擎结构

```
Game/
├── AI.py                    # GUI 适配层：AdvancedAIController（对外接口不变）
├── ai_config.json           # 唯一配置文件：难度 / 思考时间 / 采样 / 大模型顾问
├── llm_advisor.py           # 大模型顾问命令行工具
├── main.py                  # 主循环（线程安全修复）
├── game_state.py            # 规则验证 + 状态（checkmate 改用引擎，快几百倍）
├── config.py                # 走法验证器（已与引擎规则对齐）
├── jieqi/                   # 引擎（纯 Python + 标准库，不依赖 pygame）
│   ├── consts.py            # 常量、布局、位置价值表、走法表、Zobrist
│   ├── board.py             # 位棋盘、走法生成、合法性、make/unmake
│   ├── belief.py            # 暗子身份的后验分布与采样
│   ├── evaluate.py          # 局面评估（暗子取后验期望）
│   ├── search.py            # 确定性搜索（Negamax + Alpha-Beta + 静态搜索）
│   ├── engine.py            # 门面：定局化搜索 + 跨采样聚合 + 难度 / 时间控制
│   ├── gui_adapter.py       # GUI 棋盘 <-> 引擎棋盘，公开信息提取
│   ├── llm.py               # 可选大模型顾问
│   └── settings.py          # 读取 ai_config.json
└── （项目根目录）tests/、tools/   # 测试与自对弈 / 诊断工具
```

数据流：

```
GUI 棋子字典棋盘
   │  gui_adapter.gui_board_to_engine()        （只带公开信息 + 已知明子）
   ▼
引擎位棋盘 Board  ──►  clone_revealed_only()   （抹掉所有暗子真值！）
   │
   ├─ belief.Belief.from_board()  推断暗子身份池（含"被吃暗子身份未知"）
   │
   ├─ engine.Engine.analyse()
   │     ├─ EvalContext：把暗子折成后验期望
   │     ├─ 采样 K 个定局化局面
   │     ├─ 每个局面跑迭代加深 Alpha-Beta
   │     └─ 跨采样聚合（含"假杀棋"抑制）→ 选着
   ▼
SearchResult（着法 / 评估 / 深度 / 主变 / 决策树）──► GUI 主线程落子
```

## 4. 揭棋规则要点（这次踩到的坑）

依据：[象棋程序维基 Jeiqi 词条](https://chessprogramming.org/Jeiqi)、
[夸克百科·揭棋](https://baike.quark.cn/baike?id=eb2adb7ce89c4104aed25e6379bcfb28)、
[吕大帅谈揭棋](https://www.xqipu.com/node/89997)。

1. 除将帅外双方各 15 枚暗子，洗乱后按象棋原始位置摆放，**双方及旁观者都不得翻看**。
2. 暗子第一步按它**所在格子的摆位身份**行棋（摆在炮位就走炮），该步同时翻开；
   之后永远按真实身份行棋。
3. **暗子只可能待在初始格子上**——因为它一移动就会翻开。这条不变量让引擎可以把
   「摆位身份」做成按格子预计算的常量。
4. **明士、明象可以过河、可以出九宫**（"士相可以过河，增加了杀伤力"）；
   **暗士的第一步仍限在自家九宫内斜走一格**。
5. 将帅限九宫；将帅照面（对面笑）视为非法局面（等价于"对方可以吃你的将"）。
6. 兵卒：在己方半场只能向前一格，过河后可前进或左右一格（按**当前所在行**判断）。
7. **被吃掉的暗子身份保持未知**——所以 AI 也不能拿它当已知信息。
8. 胜负：将死、吃掉将帅、无棋可走（困毙）、将被离开九宫均判负；
   连续 40 回合无吃子判和。

> 旧代码里 `config.validate_advisor()` 把暗士限制成四个固定走法、明士无限制、
> 暗象按田字走没有过河限制——现在 `config.py` 与引擎
> `jieqi/consts.py` 已完全对齐，并由 `tests/test_rule_consistency.py`
> 对随机局面做 90×90 逐格比对，防止以后再次跑偏。

## 5. 不完全信息怎么处理（为什么 AI 不再作弊）

* **走法是公开信息**：暗子按摆位身份走、颜色公开、将帅始终明牌。
  所以走法生成、将军判定、困毙判定都不需要暗子真值——引擎只在公开信息上搜索。
* **材料按"它能干什么"估值**：暗子在翻开之前，**实实在在**就是它摆位身份的那个子
  （暗车能横冲直撞、能吃子），所以材料项直接用摆位身份的价值
  （`rule_ident`），而不是"剩余暗子池的后验期望"。

  > **这一条是真实反馈改出来的。** 早前用后验期望估值：一枚暗车期望只有
  > `(900+450+450+450+200+200+100×5)/15 ≈ 529`，也就是"半辆车"。后果是
  > **翻开暗车看着不亏**（529 → 随便什么身份）、**暗马可以随手丢**（只算 293
  > 而不是 450），于是引擎开局就爱翻暗车、还弃暗马。改成摆位身份之后，
  > "翻暗车翻出兵"变成实打实掉 800，保留暗车就成了引擎的自然选择。
  >
  > 实测（自对弈开局阶段，翻暗车的次数）：**8 次/4 盘 → 2 次/4 盘**。
  >
  > 那"对手不知道我藏着什么"这个信息优势呢？它体现为：**翻开的代价是真实的，
  > 而保留暗子是免费的选择权**——所以"留着"天然占优，不需要再额外加奖励项。
* **"翻开之后会怎样"用采样覆盖**：从后验分布里抽 K 个定局化局面
  （每个暗子格均匀无放回地分配身份），分别做确定性搜索，再跨采样聚合。
* **抑制"抽奖式杀棋"**：如果只有少数采样看到杀棋，说明这手杀依赖"某个暗子恰好是
  什么"，不是真杀。此时把这些样本的分值按"非杀样本的中位数"处理
  （`Engine._stabilise_mates`）。这条修复把之前出现的 `+250382` 这类畸形评分
  彻底消掉了。
* **被吃暗子的身份默认不利用**（`use_hidden_captures=false`），
  与"双方都不得翻看"的规则一致；打开它只会让 AI 占便宜。

这套设计有结构性保证：`Engine.analyse()` 第一件事就是
`board.clone_revealed_only()` 抹掉暗子真值，之后搜索只看到"暗子 + 摆位身份"。
`tests/test_engine.py::test_hidden_identity_does_not_change_result`
用两副只有暗子真值不同、公开信息完全相同的棋局验证：AI 的选着和评分**逐位相同**。
`tests/test_engine.py::TestHiddenPieceValuation` 另外钉住"暗车必须按车价估值"
与"翻暗车翻出兵时评估要真的下降"。

## 6. 配置指南（`Game/ai_config.json`）

```jsonc
{
  "ai": {
    "difficulty": "normal",      // easy / normal / hard / expert
    "time_limit": 2.0,           // 每步思考秒数；null = 用难度预设
    "samples": 2,                // 暗子采样个数；null = 用难度预设
    "max_depth": null,           // 最大深度；null = 64（基本等于不限）
    "seed": null,                // 固定后整步决策可复现（含低难度随机性）
    "emit_decision_tree": true,  // 写 decision_tree.json（tree.html / 1.py 可用）
    "verbose": false,            // 打印每个候选着法的详细分数
    "use_hidden_captures": false,// 见第 5 节，默认关
    "weights": {}                // 覆盖评估权重，见 jieqi/consts.py 的 EVAL_WEIGHTS
  },
  "llm": { "enabled": false, "...": "见第 7 节" }
}
```

难度预设（`jieqi/engine.py` 的 `DIFFICULTIES`）：

| 难度 | 思考时间 | 采样 | 深度上限 | 其他 |
|---|---|---|---|---|
| easy | 0.5s | 1 | 2 | 关闭静态搜索/空着裁剪，选着带随机（可被击败） |
| normal | 2.0s | 2 | 64 | 完整搜索 |
| hard | 5.0s | 4 | 64 | 加方差惩罚（更稳健） |
| expert | 10.0s | 6 | 64 | 更强的方差惩罚 |

调节建议：

* **游戏里直接按键切换**：`1` = 简单、`2` = 普通、`3` = 困难、`4` = 专家
  （下一回合生效，底部会提示）。`ESC` 在人机对战 / 双人对下之间切换，`空格` 悔棋。
* **想更强**：调大 `time_limit`（最直接），或把 `samples` 降到 1~2 让每个采样更深。
* **想更快/更弱**：`difficulty: "easy"`，或 `time_limit: 0.3`。
* **实测结论**：2 秒预算下采样数 1 与 4 的对局胜负基本持平（见第 8 节），
  所以默认取中间值 2，优先保证一点深度。
* `weights` 可以在不动代码的情况下微调棋风，例如 `{"hanging": 0.35, "tempo": 12}`。

### 7.-1 棋盘上下的「被吃棋子」展示条

需求：**在棋盘上下两侧显示被吃掉的棋子**，而且要尽量省纵向空间。

* 上条 = **我方被吃**（对方吃到的子），标签靠左；下条 = **对方被吃**
  （我方吃到的子），标签靠右。棋子都朝外侧排，与棋盘中央离得最远，
  不会让人误以为标签属于棋盘。
  为什么是"上=我方"：棋盘是"我方在下方"的视角，**靠近自己的那条（下面）
  摆自己吃到的战利品**，与中国象棋软件的惯例一致
  （旧版正好反过来，用户一眼就看出来了）；
* 每条外缘还有一道**属于那一方的颜色**（红/黑），标签也用同色——只靠图标颜色
  是不够的，暗子图标两边都是深色；
* **同种棋子合并成一枚图标 + 右上角数量角标**（`卒²` = 两个卒被吃、
  `暗²` = 两个暗子被吃）。所以**一条只需一行**，高度 48px；
  归并键是 `(颜色, 兵种)`，红黑绝不混（车 ≠ 車）；暗子按颜色各自归成一组，
  因为它们的真实身份对双方都不可知，界面上也只能是同一个背面；
* 排序：先按兵种权重（车/炮/马/相/仕/兵 在前），再按数量多的在前——顺序稳定，
  不会因为吃子先后不同而跳来跳去；暗子垫底（未知身份不该抢眼）；
* **明子被吃 -> 直接画真身图标**（和棋盘上同一套图，按 `STRIP_ICON` 缩放）；
* **被吃的暗子 -> 只画"暗子"背面图标**：按通行规则被吃的暗子双方都不得翻看，
  界面也绝不能把真身画出来（否则等于偷看，AI 与人类的信息就不对称了）；
* 角标只在数量 > 1 时画（单枚不画"1"，免得全是噪音）；一行排不下的**种类**
  在标签里报（`对方被吃 12 枚（另 3 种未画出）`），绝不会画到条外面去；
* 展示内容**跟着当前显示的手数走**：浏览历史时不会把后面几步的吃子也算进来
  （`gs.capture_piece` 在 `goto_ply` 时不会恢复，所以展示条是按
  `move_history[:ply]` 重放统计出来的，见 `gui_adapter.captured_gui_pieces`）；
* 这两条不参与点击命中，`button_at()` 对它们返回 `None`。

### 7.D 坐标记法：全项目统一成 `a0`~`i9`（与 UCI 的 `bestmove` 逐字一致）

需求原话："把我们的走棋记录、棋盘编码和 abj 引擎的 FEN 格式接轨，
我们也用 1-9、a-h 记录棋子的位置。"
（当时是为了跟外部引擎对接；**那个引擎后来整体移除了**，见 §12，
但这套记法本身与它无关，继续作为全项目唯一口径。）

以前同一格棋子在项目里有**三种写法**：界面记谱是 `(行6,列0)`、棋谱 JSON 是
`[6, 0]`、而 UCI 方言的着法是 `a3a4`。三种写法各写各的，对照一次要换算三次，
而且**极易搞反上下**。现在统一成一套：

* **列用字母 `a`~`i`**（从左到右，内部 `col 0` = `a`，不需要翻转）；
* **行用数字 `0`~`9`**（红方底线是第 0 行）。行号是 **0 起**而不是 1 起，
  这是实测结论：rank 0 是合法值（开局常见 `f9e8`、`b0c2`）；
* 一格写作 `b3`，一手写作 `b3c3`（与 UCI 的 `bestmove b3c3` **完全相同**）。

真相来源只有一个模块：[`jieqi/notation.py`](jieqi/notation.py)。
`board.move_str` / `parse_move_str`、棋谱的 `from`/`to`、面板走棋记录、
提示词、训练样本全部转调它——**不再有第二份实现**
（第二份实现就是"哪天只改了一边"的温床）。

改动清单与兼容性：

| 位置 | 之前 | 现在 | 旧数据还能读吗 |
|---|---|---|---|
| 面板走棋记录 | `暗炮(2,1)-(4,1)` | `暗炮 b7b5` | — |
| 棋谱 JSON `moves[].from/to` | `[2, 1]` | `"b7"` | ✅ `_move_coords` 两种都认 |
| 提示词棋盘图 | `列0 列1 …` / `行0 …` | `a b c …` / `行9 … 行0` | — |
| 提示词候选着法 | `(4,2)->(4,4)` | `c5->e5`（主变 `c5e5`） | — |
| 训练样本 `move` | `[4,2,4,4]` | `"c5e5"` | — |
| 大模型回答里的 `move` | `"(4,2)->(4,4)"` | `"c5e5"` | ✅ 解析器两种都收 |
| 中文记谱 / 棋盘文本 | `(2,1)->(4,1)` / `列0` | `b7->b5` / `a b c …` | — |

**老棋谱照样能导入**：`record._move_coords()` 先按新记法解，失败再按老记法
`[r, c]` 解，所以 `20261008-*` 那几份（换记法之前存的）不会有任何影响
（部署端实测：50 手的老棋谱导入正常）。

### 7.G 复盘的走子路径箭头 + 棋盘外围坐标（都按同一套记法）

用户要的两件事，一起说是因为它们共用同一套坐标口径
（`jieqi/notation`，列 `a`~`i`、行 `0`~`9`）：

**1）棋盘外围的坐标**：四边都标一份（上下 `a`~`i`、左右 `0`~`9`），
口径与走棋记录、棋谱、引擎输出**逐字一致**，看到 `b7b5` 就能在盘上直接找。
红方底线是第 **0** 行（黑方视角整盘 180° 翻转时，行号跟着棋盘一起翻，
所以抬头看一眼就有对应的行列号，不用心算）。原来底部是汉字数字
（九八七六…）、顶部是全角数字，与记录里的写法对不上——那才是"看不懂"的根源。

**2）回顾棋局里的移动路径箭头** —— **已在后续轮次按用户要求去掉**
（"效果不是很好，先去掉"）。当时的做法是 `Renderer._draw_move_path` 从起点到
终点画一条带箭头的折线（马走日会拐一下），棋盘页与「回顾棋局」浮层都画。
整个箭头体系（`_draw_move_path` / `_move_waypoints` / `_arrowhead` /
`_MOVE_ARROW_*` 常量）以及 `config.py` 里的 `move_arrow` 配色令牌都已删除，
不再保留"半死不活"的实现。
**保留下来的是**「上一步的四角标记」（`_draw_corner_marks`），
并且改成**支持缩放**，所以"回顾棋局"浮层里的大棋盘也能正确画出角标。

回归测试：`tests/test_renderer.py`（坐标文案 / 四角标记 / 复盘叠加层能画）。

### 9.13 同一批修掉的：大模型着法的两个符号/校验 bug

与"每方一个引擎档位"直接相关，详见 7.F：

* `_adopt_llm_move` 乘的是"走子方符号"，而 `SearchResult.score` / `verdict`
  是**红方视角** → 黑方走时等于翻了两次（"黑方走出好棋，面板却说红方大优"）；
* `_consult_llm` 那条同步路径**没有合法性校验**，非法的"大模型建议"会被原样
  落盘（旧测试里那条"非法建议"用例喂的其实是 `(0,0)->(9,8)` 两个空格，
  所以一直没暴露）。

### 7.F 对局方式：**每方各挑一个引擎**（人工 / 本机 / 大模型）

需求原话："支持切换自己的引擎，对方的引擎，大模型三种对局方式，
切换到哪种就完全应用那个引擎的招法。"
（原话里"对方的引擎"当时接的是外部引擎；**那一档后来整体移除了**，见 §12，
现在共三档。）

实现落在"**红、黑两方各自一个档位**"上（不是全局一个开关）：

| 档位 | 走子行为 |
|---|---|
| `human` 人工输入 | 由玩家自己点棋子（默认，红方） |
| `python` 本机引擎 | **完全采用**它的招法（默认，黑方） |
| `llm` 大模型 | **完全采用**大模型推荐的招法 |

**唯一真相来源**：`GameState.side_engines = {'red': ..., 'black': ...}`
（档位定义、可用性、文案都在 `jieqi/engines.py`）。
老的 `gs.ai_mode` / `gs.ai_color` **保留为派生属性**——`enable_ai('black')`
这类老调用与 15+ 个老测试一字不改照样对，但不会再出现"两个字段各说各话"。
`gs.reset()` 默认**保留**玩家挑好的档位（换阵营/重开不该把设置吃掉）。

**唯一分岔点**在 `main._move_for_current_side()`，每条分支只用一个引擎：

```python
source = gs.side_engine(gs.current_player)
if source == 'llm':       controller.analyse_llm(side)
elif source == 'python':  controller.analyse_python(side)
```

**"完全采用大模型招法"以前做不到**：旧实现只接受"本来就在引擎候选里"的
着法，等于还是引擎在下棋。现在这一档收下全部合法着法，并且
**不允许非法着法落盘**：

1. 在候选里 → 直接采用（分数沿用候选）；
2. **不在候选里但合法** → 照样采用，分数用 `Engine.score_move` 现算
   （一次浅层搜索，复用"把其余根着法全放进 forbid"的机制）；
3. 非法 / 没给 / 调用失败 → 退回本机引擎，并把"本步由本机引擎代走"写进
   notes 与面板（复盘时看得出这一手不是大模型下的）。

顺手修掉两个符号 bug（都与"每方一个引擎"直接相关）：
`_adopt_llm_move` 以前乘的是"走子方符号"，而 `SearchResult.score` /
`verdict` 是**红方视角**——黑方走时等于翻了两次（"黑方走出好棋，面板却说
红方大优"）；`_consult_llm` 那条同步路径索性**没有合法性校验**，
非法的"大模型建议"会被原样落盘。两处都有回归测试
（`tests/test_llm_plays.py`）。

**界面**：启动页左列两行 `红方引擎 / 黑方引擎`，每行三枚 chip。
用不了的档位**灰掉并写明原因**（例如"大模型模块不可用"）；
中局热键 `E` 切红方、`T` 切黑方，`cycle()` **只落在可用档位上**
（否则按一下"没反应"，是最难查的一类交互 bug）。
顶栏状态行改成 `红:人工  黑:引擎` 这种每方一段的写法。
每一手都会把自己的档位写进棋谱（`moves[].engine`），复盘时说得清"谁下的"。

**引擎拿不到着法时怎么办**：不替这一方乱走一步，而是把这一方**切回人工输入**
并在提示里说明原因——否则 `should_auto_move()` 每帧都为真，会变成"一秒刷
几十条错误提示"。`tests/test_engine_modes.py` 覆盖了这条。

### 7.H 启动页：阵营选项**去掉**，只留一个「开始游戏」

用户原话（两步）：

1. "揭棋默认红方先手，当你加了自主选择红黑双方是玩家角色后，就不需要红方
   先手或者黑方先手的启动选项了。因此首页两个按钮合并为一个开始游戏按钮。"
2. "去掉我执红或者我执黑选项，太啰嗦了，有需要我会自己调的。"

于是启动页右列最终就三个动作按钮：**开始游戏 / 继续上一局 / 载入棋谱**。

* 原来两个大按钮「执红先手 / 执黑后手」**点一下就直接开局**——等于两个"开始"，
  又没有任何确认机会（点错就把上一局冲掉）；
* 中间版本试过"两枚 chip 选 + 一个开始按钮"，但那一行仍然是重复信息
  （默认就是红方先手），所以按用户要求整行去掉；
* **换边只留两个入口**，都不占界面位置：
  `Game/ai_config.json` 的 ``ai.player_side``（``"red"`` 默认 / ``"black"``），
  或中局按 **`C`** 一键换边（``side:flip`` 命令 → ``main.flip_player_side``）。

换边时会**顺带把对局方式摆正**（``GameState.set_player_side``）：玩家那方设成
人工输入，对手那方沿用原来的档位。不这么做就会踩一个很隐蔽的坑——只改
``player_side`` 而 ``side_engines`` 还是默认的"红人工 / 黑本机引擎"，玩家改执黑
之后**两边都是人工**，AI 一步都不会走，看起来像"电脑坏了"。规矩是"把对手原来
由谁出招整体搬到新的对手那一方"，所以"黑方=大模型"时换边会变成"红方=大模型"，
档位不丢。

顺带删掉了只服务于旧阵营按钮的东西：``StartLayout.side_rects``、
``Renderer.side_selection_rects``、``InputHandler._handle_side_selection_click``。
``_handle_game_click`` 里那句"AI 回合禁止玩家代走"的判断也从
``current_player == ai_color`` 改成 ``not gs.is_human_side(current_player)``
——两方可以各配不同引擎之后，已经没有"唯一的 AI 方"这个说法了。

> ⚠ **这一节描述的功能已在后续轮次整体移除**（外部引擎 / 分支棋谱），
> 保留原文只为记录当时的判断依据。以 **§12** 为准。

### 7.1 步数自由切换 + 点评按步数存档
`GameState.positions[k]` 保存第 `k` 手之后的**完整局面快照**，
`ply_comments[k]` 保存**针对第 `k` 手之后那个局面**的大模型点评。
于是：

* 前进/后退只是移动指针 + 恢复快照，**不需要重放、也不会丢历史**，
  所以"回退之后还能再前进回去"；
* 回到第 `k` 手时，面板上显示的就是第 `k` 手的点评与评估——
  点评是**跟着步数走**的；
* 那一步没有点评（例如玩家自己走的）时，退回显示上一步的点评，
  因为上一步的点评解释的正是"为什么会走到这里"；
* 在历史局面上走子＝从这一步**开新分支**：后面的记录与点评一起截断；
* 浏览历史期间**暂停 AI 走子、也不请求大模型**；点「最新」回到最新局面后，
  如果轮到 AI，它会照常继续走。

> **"该谁走"是按手数算出来的，不是从快照里读的**（真 bug）：快照存的
> `current_player` 是"当时轮到谁"，也就是**刚走完的那一方**。于是
> "AI 走完 → 玩家点上一步 → 点下一步回到最新"会让 `current_player` 变回
> `ai_color`，AI 又走一步（用户报的"黑方连走两步"）。
> 修法：`_side_to_move_at(ply)` 从 `move_history[ply-1]['side']` 反推；
> 翻手按钮也改成**按回合**（`goto_round`），落点永远是整回合边界。

一个容易踩的坑：点评是**异步**回来的，通常等 AI 已经落子之后才到，
那时 `gs.ply` 已经前进了一步。所以点评挂的是「**分析时所在的那一步**」
（控制器把它记在 `comment_ply`），而不是"当前步数"，否则两手的点评会串台。

**回退不访问模型**：

1. 丢弃在途的点评请求结果（用代号校验，回来时发现局面已变就直接丢掉）；
2. 显示的点评按当前步数取，不会用最新的覆盖面；
3. 不会因为回退本身发起任何请求。

另外，如果玩家在 AI 思考期间切换步数，那份计算结果会按**步数**校验作废，
不会被错误地落到别的局面上。

`base_url` 填任意 OpenAI 兼容的 `chat/completions` 端点，`model` 填模型名。

已验证可用的一组（DeepSeek）：

```jsonc

  "enabled": true,
  "base_url": "https://api.deepseek.com",
  "api_key": "sk-...",
  "model": "deepseek-chat",
  "timeout": 20.0,
  "mode": "explain",
  "blend_weight": 0.0
}
```

### 8.1 三种参与程度
| 开关 | 行为 | 延迟 |
|---|---|---|
| 只点评（默认，`blend_weight: 0`） | 异步点评，**完全不影响选着** | 不增加走子延迟 |
| 影响选着（`blend_weight > 0`） | 它的推荐会在引擎候选上加分（上限 +50 厘兵），仍由搜索定夺；同步请求 | + 一次请求 |
| **应用大模型招法**（顶部开关 / 按 `K`） | **直接下它推荐的那一手**；它给的着法如果不在合法候选里就退回引擎着法 | + 一次请求（约 1~2 秒） |

「应用大模型招法」也可以直接写进配置（重启后仍生效）：

```jsonc
"ai": { "apply_llm_move": true }
```

安全性：无论哪种模式，大模型的着法**只能在引擎已经验证过的合法候选里挑**，
所以它不可能让 AI 走出违规着法。它给出的坐标越界/不在候选里都会被拒绝并说明原因
（`result.notes` 里能看到「不在合法候选里，已按引擎着法」）。

### 8.2 它看得到什么（上下文）

为了让点评"记得住整盘棋"而不是每步从零开始，提示词里除了当前局面还带：

* **走棋记录**：最近 12 手（含翻子结果、吃子）；
* **评估走势**：最近几步的引擎评分与结论，用来看形势怎么变化；
* **上一步点评**：它自己上次说的话，要求前后自洽，改判必须说明理由。

系统提示词里明确要求：点评必须体现"和上一步相比变化了什么"。

### 8.3 点评只针对 AI 自己的招法

这是重做时专门定下的一条规则：**面板上的点评永远是"AI 解释自己这步棋"**。

* 提示词里带上 `点评对象：AI 自己的招法`（快照字段 `comment_target`），
  系统提示词要求模型用"我方"视角解释这步棋的意图、风险、对手应手，
  并**明确禁止它去指导人类一方该怎么下**；
* 点「让 AI 替我走这步」时走的是同一个引擎，但调用的是
  `get_best_move(comment=False)` → `analyse(comment=False)`，
  **一次模型请求都不发**（同步的"应用大模型招法"分支也一并跳过）。
  否则玩家会看到"我走棋，AI 却在点评"，根本分不清点评在说谁。

实测（`_bench/verify_ai_only_comment.py`，真实 DeepSeek）：

```
1) AI 走棋：着法=8193  发起请求=1
   comment_target = AI 自己的招法
   [点评] 我方选择用7路砲长驱直入吃红方刚翻开的兵……红方上一手在(0,0)翻出红兵
         并走到(1,0)，等于把一枚明兵送到我方砲口下，我吃兵后既得实利又压住红方右翼。
2) 替玩家走棋：着法=9003  发起请求=0
3) 替玩家+应用招法：着法=11084  发起请求=0
```

回归测试：`tests/test_llm_context.py::TestCommentOnlyForAiMoves`
（AI 自己走棋必须请求点评；`comment=False` 时连同步路径都不许发请求）。
浏览历史时，上下文也只取到**当前显示的那一手**为止，不会把后面的棋透给它。

**点评显示在哪里**：AI 每步走完后，点评显示在**右侧信息面板底部**
（标题「大模型点评（仅参考）」，浏览历史时会标注是第几手），
同时打印到控制台 `[揭棋AI][大模型] ...`。
请求是异步的，不会拖慢走子（「应用大模型招法」模式除外，那个必须等回复）。

**翻子一定能被看懂**：`move_history` 存的是落子**前**的棋子快照，所以一步"翻子"
在里面仍然是"暗子"。旧版提示词因此写成
`上一手：(3,4) -> (4,4)（棋子 暗子）`，与棋盘图上那一格已经是明子自相矛盾，
模型于是说"上一手为暗子，可能是兵或炮"。现在：

* 走棋记录里写成 `红暗炮→车 (2,1)-(4,1)`；
* 提示词里写成 `上一手：(2,1) -> (4,1)（棋子 暗子，翻开后是 红车）`；
* 棋盘图**每一行都自带列号**（`列号: 列0 列1 …` / `行0 …`），并明确约定
  **「車?」= 未翻开的暗子（问号前是摆位身份）**、
  **不带问号 = 已翻开的明子，不要再说它身份未知**。

### 8.4 归属不会认错：局面事实表 + 点评质检（这一版的重点）

**问题**：模型经常分不清"这枚车是我方的还是对方的"，点评里出现
"我方车被对方的卒挡住"这种红黑颠倒的句子，玩家越看越糊涂。

**根因**：旧版只给模型一张棋盘图 + 一堆坐标，**归属要它自己从位置推**——
同型子（双方都有车马炮）字形又不同，一旦推错就整段胡说。这属于"让模型做本地
就能算准的事"，必然出错。

**做法分三层，先把事实算准，再让模型只负责表达**：

1. **局面事实表**（`jieqi/gui_adapter.py::llm_facts` + `jieqi/llm.py::render_facts_text`）
   引擎在本地把下面这些全部算好、写成不含歧义的中文，提示词里原样贴出来：

   * 本轮走棋方 + **AI 执哪一方**（"下文「我方」= 黑方，「对方」= 红方"）；
   * 我方的明子清单（`黑士(行6,列1)` …）、暗子清单（`暗卒? ×5：(行6列0)、…`）；
   * 同样一份对方清单；
   * 被吃明细（明子记身份，**被吃的暗子只记数量**——规则上不得翻看）；
   * 将军情况、明子子力对比；
   * **攻击关系**（用引擎的 `Board.is_attacked` 算：
     "本方(黑方)正被对方攻击的子：黑馬(行8,列7)、1 枚暗子"）；

2. **候选着法的自然语言注解**：每条候选都写成
   `本方(红方，即 AI 执的一方) 走 本方(红方) 的「车」 从 (3,7) 走到 (2,7)，
     吃掉对方的「黑馬」，引擎评分 +582`——
   谁走、哪一方的哪枚子、吃什么，全部由引擎填好，模型照抄即可；

3. **点评质检 + 自动改判**（`check_comment` / `repair_comment` / `suggest_checked`）：
   拿到点评后逐句核对归属，出现硬伤就处理：

   | 情况 | 处理 |
   |---|---|
   | "我方车"但我方根本没车（对方才有） | 若能判定是**整句红黑说反**，自动对调「我方/对方」与红黑字形后采用 |
   | 改不回来（只错一半） | **定向重问一次**：把问题清单作为 system 提示追加给模型 |
   | 重问仍不合格 | **清空点评**，面板上不显示——宁可不说话，也不能误导玩家 |
   | 同步路径（应用大模型招法 / blend） | 同样质检；改不回来时在末尾加 `（!! 这段点评与局面归属矛盾…）` |

   质检只认**可证明的矛盾**（显式归属词 + 兵种字对不上事实表），
   刻意不做语义猜测，宁可漏报也不误报——误报会把好点评也丢掉。

**其它配套**：

* 走棋记录每行都标 `[我方]/[对方]（AI）`，模型不必自己推"这步是谁走的"；
* 快照里做了一次**归属自检**：如果候选着法的起点不是"走棋方自己的子"
  （外部工具传错 turn 才会发生），会在提示词里明确写出警告
  `⚠ 有 N 条候选着法的起点不是…`，让模型别为它们编归属；
* 质检开关 `llm.comment_validation`（默认 `true`，环境变量 `JIEQI_LLM_VALIDATE`）；
  控制台启动行会打印 `归属质检=开/关`。

**回归测试**：`tests/test_llm_ownership.py`（21 条）覆盖事实表完整性、
每枚子在事实表里恰好出现一次、提示词带归属注解、明暗与被吃的记账、
质检抓错/不误报、自动改判、定向重问、改不回来时清空点评。

**人工检查提示词**（不联网）：

```
python _bench/preview_llm_prompt.py 12 --out _bench/prompt_preview.txt
python _bench/check_llm_ownership.py     # 只跑归属判定与质检的自检
```

**为什么没反应**：启动时控制台一定会打印一行状态，直接告诉你是哪一种：

| 控制台输出 | 原因 |
|---|---|
| `大模型顾问未启用：ai_config.json 里 llm.enabled = false（改完需要重启游戏）` | enabled 不是 true，或改完没重启 |
| `大模型顾问已启用，但找不到 API Key：请填 llm.api_key，或设置环境变量 XXX` | key 为空 |
| `大模型顾问已启用：<model> @ <endpoint>（只点评/会按权重影响选着…）` | 正常 |
| `[揭棋AI][大模型] 大模型调用失败：...` | 网络或鉴权问题，错误原文会照抄出来 |

> 配置是在**创建 AI 控制器时**读取一次的：改完 `ai_config.json` 后要重开游戏；
> 游戏中按一次 `1`~`4` 切换难度也会顺带重建控制器并重新读取配置。

两种用法：

* `blend_weight = 0`（默认）：**只看不插手**。引擎照常选着，大模型的中文点评
  异步返回后显示在面板里。
* `blend_weight > 0`：在选着前**同步**询问模型，若它推荐的着法在引擎候选里，
  就按 `weight × 置信度 × 50 厘兵`（上限 50）加分后重排。
  注意这会引入额外延迟（模型响应时间），并且 `weight=0` 时加分恒为 0
  （`tests/test_llm_integration.py` 验证了这两条）。

安全提醒：把 key 直接写进 `ai_config.json` 是明文存储，而且**重新部署不会覆盖它**
（部署脚本把 `ai_config.json` 列为受保护文件）。更稳妥的做法是把 `api_key` 留空，
改用环境变量：把 `api_key_env` 改成你要用的变量名，然后在系统里设置它。

命令行试跑（不联网）：

```powershell
cd D:\py\Chinese Chess\Game
python llm_advisor.py --demo --dry-run      # 打印将发送的提示词
python llm_advisor.py --demo               # 真调用（需要 key）
```

## 8.5 棋谱：保存 / 导出 / 复盘找失着 / 训练样本

目标是"**这一局到底输在哪一手**"能查、而且这些棋谱以后能直接拿去喂模型。
一次对局 = 一个自包含的 JSON，逐手局面都在里面，所以事后只凭这一个文件就能
完整重放、重新分析。

### 存了什么

* `Game/records/20261007-153012-red-vs-ai.json`：完整棋谱
  （每手：谁走、从哪到哪、是否翻子、翻出什么、吃了什么、当时的大模型点评与
  引擎评分；外加**每一手之后的完整棋盘快照**）；
* 同名 `.txt`：中文记谱，给人看的（含逐手记录 + 终局棋盘 + 双方损失）；
* `index.json`：棋谱索引（列表用）；
* 训练样本（`record_tool.py train` 生成）：一行一个局面的 JSONL。

**暗子真身不落盘**：未翻开的子只写摆位身份（`hidden: true, home: "卒"`），
绝不写 `actual`——否则这份棋谱就成了"AI 作弊资料"，而它是要拿去训练的。
被吃掉的暗子同样只记数量，不记兵种。

### 什么时候存

* **对局结束（分胜负或判和）自动存**——由 `ai_config.json` 的
  **`record.auto_save`** 控制，**默认开启**：

  ```jsonc
  "record": {
    "_auto_save": "对局结束自动保存棋谱到 Game/records/，默认开启。",
    "auto_save": true
  }
  ```

  关掉之后终局不写盘，仍可随时手动保存。配置里**没写这一项、写成 null、
  或类型不对**时都按"开启"处理——宁可多存一份，也别因为配置写错丢掉棋谱；
  只有显式 `false` 才关闭。
* 随时按 **`S`** 或点右侧「**导出棋谱**」按钮手动存当前局面（未下完也能存，
  `result` 记为 `*`）；
* 按钮/快捷键都不访问大模型，纯本地写文件。

### 棋谱**永不覆盖**（这一条是硬保证）

早前有两个会**悄悄盖掉已有棋谱**的路径，现在都堵住了：

1. **同名撞车**：文件名只精确到秒（`20261008-013012-red-vs-ai`），而保存是
   直接 `open(path, "w")`。两局棋在同一秒结束、或快速连续终局，就会互相覆盖。
   → 现在 `save_record` 保存前先找一个空闲名，被占用就自动加 `-2` / `-3`
   （判定时 **json 与 txt 一起看**，否则会出现"json 是新名、txt 把旧的盖了"
   的错配）。
2. **导入后接着下**：`import_record` 原本把**导入文件的名字**写进
   `record_saved`，而终局自动保存拿它当输出名——于是"导入 A → 下完 → 自动保存"
   会把 **A 覆盖掉**。
   → 现在导入的名字记在 `imported_from`（只用于显示），`record_saved` 只记
   "**这一局自己写出来的文件**"；终局自动保存走 `unique=True`，**一定开新文件**。

三种语义分得很清楚：

| 场景 | 行为 |
|---|---|
| 终局自动保存（`unique=True`） | **永远**新开一份，绝不碰任何已有棋谱 |
| 同一局手动导出两次 | 更新**自己那一份**（`mine=record_saved` 不算被占用） |
| 不同对局撞上同一个名字 | 自动变成 `xxx-2`、`xxx-3`… |

`save_record(..., overwrite=True)` 仍可显式覆盖，只留给明确知道后果的调用方。
返回值多了 `requested` 字段（调用方原本请求的名字），这样界面提示能显示
**实际写出的**文件名而不是自己拼的。

### 操作反馈（点了必须知道成没成功）

导出/导入这类操作**不会改变棋盘**，所以早前"点了没反应"的体验很差
（真实反馈）。现在这些操作会在**棋盘上方弹一条横幅**，写清楚结果，
4 秒后自动淡出、缩回顶栏那一行小字：

* 成功（强调色边框）：`棋谱已导出到 records\20261007-223045-red-vs-ai.json`
  —— 带上真实文件名，便于直接去目录里找；
* 失败（暖色边框）：`棋谱导出失败：<原因>`、`导入失败：<原因>`；
* 自动保存同样给横幅：`棋谱已保存：<棋谱名>`。

实现上是一对很轻的约定：`GameState.set_toast(text, loud=True)` 记下
`toast_until`（过期时间）+ `toast_loud`（是否放大），渲染器在过期前画横幅、
过期后只画顶栏小字。状态类提示（"AI 思考中…"、"将军"）一律不放大，
免得每步都弹一条挡着棋盘。

### 命令

```powershell
cd D:\py\Chinese Chess\Game

python record_tool.py list                      # 列出全部棋谱
python record_tool.py show 20261007-153012-red-vs-ai
python record_tool.py show <名字> --board 30     # 额外打印第 30 手之后的棋盘

# 复盘找失着：逐手用引擎重新分析，按"落差"排序列出最可疑的几手
python record_tool.py analyse <名字> --time 0.8 --samples 2 --threshold 120

# 训练样本（JSONL；一行一个局面 = 棋盘 + 实际着法 + 合法着法 + 引擎评估 + 胜负）
python record_tool.py train <名字> -o train.jsonl
python record_tool.py train --all -o training-all.jsonl
```

`analyse` 的输出长这样（"得分"是**走子方视角**，落差 = 最佳分 − 实际分）：

```
 手数 方   实际着法                    得分  引擎最佳                    得分      落差
   8 红    (5,7)->(4,7)              -1324  (9,6)->(7,4)               -445      879
  26 红    (5,0)->(3,1)              -1583  (9,2)->(7,0)               -849      734
```

**怎么读**：暗子身份未知、搜索深度也受时间限制，单看一手落差大不一定就是错棋；
但**连续几手大落差**通常就是崩盘的起点，从那里往后看 3~5 手基本能找到问题手。

### 训练样本长什么样

```json
{"name": "...", "ply": 1, "side": "red",
 "board": ["R车* R马* R相* R仕* R帅 R仕* R相* R马* R车*", "...", ...],
 "move": [2, 7, 9, 7], "move_chinese": "红暗炮? (2,7)->(9,7)（翻开后是 红车）",
 "legal_moves": ["(2,7)->(9,7)", ...], "eval_red": null, "value": 1.0,
 "result": "1-0"}
```

* `board`：10 行紧凑写法，`R`/`B` = 红/黑，`*` = 未翻开（`R车*`），`..` = 空格；
* `value`：终局胜负（**走子方视角**，胜 1 / 和 0 / 负 -1）——这就是"局面评估"
  的监督信号；`move` 是"策略"的监督信号；`legal_moves` 方便做合法性掩码；
* 默认**不带** `hidden_truth`；确实需要"事后打标签"时才用
  `--with-hidden-truth`（带上暗子真身，**直接训练会让模型学会偷看暗子**）。

### 只留下日志、没留棋谱怎么办

`_bench/replay_log.py` 可以把日志里那一串 `最佳：(6,8)->(5,8)` 重建成局面并
逐手复查（日志若是从对局中途开始的，用 `--first-side` 指明第一步是谁走的）：

```powershell
python _bench\replay_log.py --moves-file moves.txt --analyse-last 6 --time 1.0
python _bench\replay_log.py --record 20261007-153012-red-vs-ai --analyse-last 8
```

### 导入棋谱（界面）

右侧「**导入棋谱**」按钮（或按 `I`）可以选一份 `.json` 棋谱读回来：

* 导入的是**重放**出来的对局（不是直接套用棋盘快照），所以导入之后
  上一步/下一步、回顾棋局、按步数取点评全都照常可用；
* **导入后停在开局**，用「下一步」一步步复盘到终局——棋谱多半是已经下完的，
  如果一导入就进入结算状态，界面会立刻弹出"红方胜利 / 点击任意位置重新开始"
  把整盘棋锁死，连上一步/下一步都点不了（这个 bug 真实出现过，现在有测试守着）；
* 棋谱里的**结果延后生效**：只有玩家自己翻到最后一手才结算，中途翻历史不会；
  退回开局会清掉结算状态；
* 导入后会切到「双人对下」（导入的是别人的棋局，不该让 AI 接着走）；
* 重放时每一步都会用规则引擎校验，棋谱被改坏会停下并说明是第几手；
* **终局后右侧按钮仍然点得动**：结算画面盖住棋盘时，如果连"上一步/导出棋谱"
  都点不到，玩家就只能重开一局了（这也是同一个反馈里发现的）。

## 8.6 引擎体检与棋力回归

改了搜索/评估以后，"感觉变强了"不算数，要能量。三个脚本：

```powershell
# 同样时间能搜多深、节点率多少、热点在哪
python _bench\bench_engine_depth.py --time 2 --samples 2 --count 6
python _bench\bench_engine_depth.py --count 1 --profile

# 评估函数差分：重写后的快速版必须和"逐格朴素版"逐局面完全一致
python _bench\diff_eval.py

# 自对弈 A/B：同一套代码只切换一个特性，看谁赢 + 平均深度
python _bench\ab_selfplay.py --games 10 --time 0.25 --a-no-cache --a-no-ext
python _bench\ab_selfplay.py --games 10 --time 0.25 --a-samples 1 --b-samples 2
```

这一轮体检发现的**真实性能问题**（都在 `jieqi/evaluate.py`）：

| 问题 | 影响 | 修法 |
|---|---|---|
| 评估每格都过一遍 90 格 × 多次 | 评估占搜索 65% 时间 | 只遍历**有子的格**（位掩码），受攻/被保护只遍历"被打到的格" |
| 同一局面被反复评估（迭代加深 + 转置） | 白算 | 按 `board.key` 缓存局面分（并缓存"明子统计"） |
| 数"还剩几个仕/相"要扫两遍全盘 | 每次评估多两次全盘扫描 | 一次统计完双方全部兵种并缓存；暗子数量用 `hidden_mask` 一次 `bit_count` |
| 每采样固定平分时间、一层搜不完还硬开下一层 | 采样多的时候深度被压到 3 层 | 按"剩余时间 / 剩余采样"重新平分；一层花超剩余时间就收手 |
| 静态搜索看不到"将军"之后的强制线 | 容易被突然的杀棋打懵 | **将军延伸**：一步将军延伸一层（每条线最多一次，避免长将爆深度） |
| 时间太紧还硬跑多个采样 | 每 2 秒 / 2 采样只到 3 层 | 时间不足时自动减少采样，保证每采样至少 0.6 秒 |

**实测（同一台机器、同样 2 秒 / 2 采样）**：

```
优化前：深度 3   15.4k 节点/秒     优化后：深度 4   26.2k 节点/秒
```

评估改写前后用 `_bench/diff_eval.py` 逐局面差分（240 个局面，0 处不一致），
所以"结果不变、只是更快"是有证据的。

**自对弈 A/B（12 局，0.8s/手）**：把"评估缓存 + 将军延伸"全开（B）对全关（A），
**B 5 胜 1 负 6 和**。样本小、和棋多（40 回合无吃子/三次重复判和很常见），
所以只能说明"没有变弱、大概率更强"，不能当成精确棋力提升幅度。

> ⚠ 位棋盘用的是 `STRIDE=16` 的稀疏布局：**"位的下标"不等于"格子号"**。
> 遍历位掩码必须走 `bit_to_sq`（`evaluate.py` 里有启动自检 + `diff_eval.py`
> 差分测试守着）。这一轮就踩过：直接拿 `bit_length()-1` 当格子号，棋盘下半部分
> 会算出 90 以上的下标，把 `side[]` 索引越界。

### 8.7 根节点「送杀体检」（`mate_guard`）
问题：深搜视野不够长时，会出现"评估说黑方大优、其实已经被强制杀"的崩盘；
而对方那几步将军如果是**非吃子**着法，静态搜索也补不上。

做法：在根节点选着之前，额外做一次**只看吃将、不看位置分**的小型证明搜索
（`Searcher.forced_loss_moves`）：把"走完之后对方能在 N 层内强制吃将"的着法挑出来，
只要还有别的着法不会被强制杀，就改走那一个。

几条必须记住的工程细节（都是踩出来的）：

* **它的预算必须与整局搜索分开**（`_guard_deadline` / `_guard_nodes`）。
  早期版本直接改 `self.deadline`，体检跑完之后搜索只剩零点几秒，
  **连"一步杀"都找不到了**；
* **超时要能回滚棋盘**：体检靠抛 `TimeUp` 截断，异常会把每一层递归里已经
  `make` 的着法全部跳过 `unmake`，棋盘上就留下"走了一半"的格子
  （`rule_ident == 0` 却有子），紧接着 `gen_pseudo` 直接 `KeyError: 0`。
  现在超时统一走 `_guard_rewind()`，按撤销栈深度退回体检开始时的状态；
* **别把"谁吃谁"搞反**：将死在本游戏里就是"吃将"，所以"轮到对手却无棋可走"
  算**我们**赢。早期版本检查的是"我方将还在不在"，于是**一步杀的好棋被当成送杀否掉**；
* 只在"挑中的着法会被强制杀、且还有别的着法不会"时才改判，所以正常局面里
  它完全不介入选着（`tests/test_engine.py::TestMateGuard` 两条测试守着）。

> 顺带记一条**没做成**的事：一度把将军延伸从"一条线最多一次"放开成"每层各一次"，
> 想把强制线看穿；结果连一步杀都搜不到了（双方连续将军时深度被反复回补，
> 原本能搜到的杀线反被挤出时限）。已回退，并在这个分支留了注释，
> 强制线漏杀交给上面的体检兜。

### 8.8 性能实测：瓶颈在哪、哪些"想当然的优化"是白费

要提高棋力就得让同样时间搜得更深，所以先量清楚**时间花在哪**。
工具：`_bench/bench_eval_sections.py`、`_bench/bench_bits_iteration.py`、
`_bench/check_eval_accuracy.py`。

单局面静态评估 **52 微秒**（≈ 19,000 次/秒），分段如下：

| 段 | 耗时 | 占比 |
|---|---|---|
| **攻击图 ×2（红+黑）** | **23.6 us** | **45%** |
| 材料 + 位置（只遍历有子的格） | 11.7 us | 22% |
| 其余（受攻/被保护/将帅安全/机动） | 16.7 us | 32% |
| 明子统计 | 0.1 us | 0% |

**所以瓶颈是"攻击图每节点从零算两遍"，不是搜索算法。** 待办按收益排序：
① 让 `evaluate` 只算一次攻击图（现在红黑各算一次，能省一半）；
② 攻击图改成 `make/unmake` 时增量维护（省掉重复计算，风险高，要差分测试守）；
③ 只遍历有子的格、把 `SQ_BIT[s]` 位判断换成收缩掩码。

**两条已经证伪的路子（省得以后再试）：**

* ❌ **重写 `_bits` 生成器**。profiler 显示它占 14.6%（135 万次调用），看着像瓶颈；
  单独测速后发现换掉只快 **1.01x**——profiler 统计的是生成器的"累积时间"，
  把调用方的活也算进去了，是**假象**。
* ❌ **加采样个数**。32 局同时间自对弈 A/B（`_bench/ab_selfplay.py`，
  samples=1 vs 2，两批共 32 局）：**1 采样 20 胜 6 负 6 和（胜率 77%，p≈0.006）**，
  而两者实际深度几乎相同（3.54 vs 3.45）。原因：时间被分摊到两次独立定局化上
  并不会搜得更深；而"跨不同世界取平均"会把只在部分世界成立的战术稀释掉。
  **所以 `samples` 默认改成 1**（配置里留了说明）。

> 教训：**先量再改**。这一轮两个"看起来最该优化"的地方，一个收益 1.01x、
> 一个方向反了；真正的瓶颈（攻击图占 45%）反而是 profiler 里看着不显眼的那个。

### 8.9 翻子权重（`reveal_weights`）怎么定出来的

`jieqi/reveal.py` 那套"翻子搜索加成"照 AB-JChess 的公式实现之后，**权重不能拍脑袋**
——它是线性组合，量级错了会从"有用"直接变成"有害"。工具是
`_bench/tune_reveal.py`，两个模式：

* `--batch`：把几组候选分别和"全关"比一遍（**同一局集**，所以组间可比）；
* 默认：从起点开始分组爬山（每个参数试"加减一步"，只有置信区间整体高过 0.5
  才升级——宁可不动，也不被噪声推着走）。
* `--workers N`：多局并行（每局独立引擎实例，**不影响结果**，只影响速度）。
  实测把一轮从 **19 分钟压到 2.2 分钟**。

`--batch` 的成绩（每格 20 局，并行 6）：

| 候选 | 得分率 | 95% 区间 | 结论 |
|---|---|---|---|
| `base 15 / phase 20` | **0.818** | [0.52, 0.95] | **显著更好** |
| `base 30 / phase 40`（我最初"想当然"的起点） | 0.500 | [0.25, 0.75] | 等于没用 |
| `base 30 / phase 40 / unknown 20 / reduction 2` | 0.429 | [0.21, 0.67] | 分不出 |
| `phase 80` | 0.182 | [0.05, 0.48] | **明显更差** |
| `base -30 / phase -40` | 0.071 | [0.01, 0.31] | **明显更差** |

> 教训（这一轮的第三次同类教训）：**方向对不等于量级对**。
> 我按 AB-JChess 的参数量纲猜了一组 `base 30 / phase 40`，实测毫无作用；
> 砍一半才显出效果，再加倍就有害。所以任何"看起来该有加成"的项，
> 都必须先用 `--batch` 量一遍，再谈调优。

**但最终的结论是否定的——`reveal_weights` 保持关闭（空配置）。**

`--batch` 的赢家（`base 15 / phase 20`）换到**新局集**上打 48 局就没复现：

| 局集 | `base 15 / phase 20` | `base 15 / phase 20 / unknown 30` |
|---|---|---|
| seed 8800（发现它的那一批，20 局） | **0.818** [0.52, 0.95] | — |
| seed 13570（新局集，48 局） | **0.433** [0.27, 0.61] | **0.429** [0.28, 0.59] |

两组都跨 0.5，即**都没有显著好过"关闭"**。所以配置里 `reveal_weights` 与
`reveal_quiet_weights` 都留空——**宁可不要这个加成，也不把没验证过的权重
留在配置里**（一个"看起来在干活"的权重比没有更难发现它其实有害）。

> ⚠ 这是本主题**第四次**同类教训，而且是最值得记的一次：
> 20 局的"显著更好"（0.818）在 48 局上翻成了 0.433。小样本上"显著"两个字
> 靠不住——**先在小局集上筛，再在大局集上确认**，否则就是在噪声里挑赢家。
> 复现命令（约 8 分钟）：
> `python _bench/tune_reveal.py --batch --only 小加成 --games 48 --workers 6 --seed 13570`

## 9. 修过的两个真 bug（都有回归测试）

### 9.1 AI 送将：走进将帅射线给敌方炮当炮架

**症状**：真实对局里 AI 走出一手"送将"，红炮直接把黑将打死。

**根因**：为了速度，`legal_filter` 用了"关键格"优化——只有从将帅出发的
射线上**前两个己方子**被移开时才需要真的 `make/unmake` 验证，其余着法直接
判为合法。这个推理漏掉了一整类着法：**棋子走到将帅射线上、正好给对方炮当
唯一炮架**。移开挡子会让将帅暴露，**走进射线同样会让将帅暴露**。

复现出来的局面（`tools/debug_legal_filter.py`）：

```
黑将 (8,4)，红炮 (6,4)，(7,4) 空着   -> 0 个炮架，不将军
黑暗象 (9,2) 走到 (7,4)              -> 1 个炮架，红炮立刻打死黑将
```

旧实现里这一手被当成合法着法，AI 于是"送将"。

**修法**（`jieqi/board.py`）：`legal_filter` 现在用一个保守超集
`_risky_squares(side)` 决定哪些着法必须逐个验证，包含三类：

1. 将帅自己所在的格子，以及射线上的前两个己方子（原来就有的那类）；
2. **将帅与敌方炮之间的所有空格**——走进去就凑成"恰好一个炮架"；
3. **蹩住敌方马腿 / 塞住象眼、而那匹马或象的目标正是我方将帅**的己方子——
   移开它等于自己把马腿放开（这一类也是原来漏掉的）。

**验证**：`tests/test_attack_truth.py` 里用**另一套实现**（逐个 `make` 后判断、
以及直接生成伪合法着法看目标格）做差分，在随机的 14 个种子 × 40 手 × 双方
局面下要求两者**完全一致**，并额外构造了炮架/牵制/蹩马腿的定点局面。
`tools/legality_audit.py` 再往前一步：用 **GUI 自己的规则**（`gs.validate_move`
+ `gs._check_check` + `gs._check_face_to_face`）去复核每一局里 AI 的每一步，
并要求"走完之后自己的将帅不能被攻击"。实测 20 局（AI 执红执黑各半）全部通过。

### 9.2 面板上出现 +500420 这种离谱评分

**症状**：日志里出现 `评估：+500420（红方胜势）`。

**根因**：采样数只有 2 时，"2 个采样里有 1 个看到杀棋"占 50%，
而原来的判定是 `len(mates) * 2 >= len(vals)`，也就是"**≥ 一半**就算确认"，
于是 1/2 被当成真的杀。平均分变成 `(999998 + 842) / 2 ≈ 500420`。

**修法**（`jieqi/engine.py::_stabilise_mates`）：改成**严格过半**
（`len(mates) * 2 > len(vals)`）。2 个采样里 1 个看到杀 → 不算杀，
那一步按"非杀样本的中位数"处理；4 个采样要 3 个才算。

### 9.3 退回历史后"该谁走"错了 —— 导致红方（或 AI）连走两步

**症状**（用户报的）：开局 → 红走一步 → 黑走一步 → 点「上一步」，
界面**提示轮到红方**，于是红方又走一步 = **红连走两步**。
（另一次表现是 AI 连走两步。）

**真正的根因**（第一次我误诊成"回合判据"问题，第二次才找准）：
`GameState.goto_ply` 直接读快照里的 `current_player`，而快照是在 `move_piece`
里"**走完这步之后**"存的——那一刻 `current_player` 还是**刚走完的那一方**
（切换是调用方在之后才做的）。所以退回一步后，轮次显示成了"刚走完的人"：

| 位置 | 快照里的 current_player | 实际该谁走 |
|---|---|---|
| 开局（0 手） | red | red ✅ |
| 第 1 手之后 | red（红刚走完） | **black** ❌ |
| 第 2 手之后 | black（黑刚走完） | **red** ❌ |

**修法**：轮次**从走法历史推**，不读快照字段。红先、之后逐手交替，
所以"该谁走"永远是"刚走完的那一方的对面"：

```python
def _side_to_move_at(self, ply):
    last = self._last_mover_at(ply)      # move_history[ply-1] 的 side
    return 'red' if last is None else ('black' if last == 'red' else 'red')
```

`goto_ply` 里 `self.current_player = self._side_to_move_at(target)`。
为此给 `move_record` 显式加了 `'side'` 字段（**不靠棋子颜色去推**）。

**同时按用户要求改了导航粒度**：按钮从「上一步/下一步」改成
**「上一回合/下一回合」**（一回合 = 红黑各一手）——按手翻会停在
"红走完、该黑走"的半路上，看起来就不像一整步。`main.py::goto_round(delta)`
按 ±2 手翻并夹在 `[0, total_plies]`，落在整回合上（偶数手），
所以落点永远是"轮到红"。

**辅助防线**：`main.py::can_ai_move()` 额外要求
"轮到的一方不能就是刚走完的那一方"（`_last_mover() != current_player`）。
根因修掉之后这条已经不会触发了，但留着当不变式守卫。

回归测试：`tests/test_nav_turn.py`（10 条，含"每一手的轮次都要对"、
"回合翻必须落在整回合上"、"回到最新后 AI 不该再走"）。
`tests/test_ai_turn.py`（7 条）里原本断言旧行为的
`test_back_and_forward_does_not_hand_the_turn_to_ai` 也一并更正为断言**修复后**的正确行为。

### 9.4 开发过程**误删用户棋谱**（工具层护栏）

**症状**：我在"跑完测试/部署完"之后顺手执行 `Remove-Item Game\records\*`，
把用户真实的棋谱删掉了——而 `Remove-Item -Force` **不进回收站，无法恢复**。
这是纯粹的破坏，不是 bug，但必须堵住。

**修法**：

* 新增 `tools/record_safety.py`：**任何**清理动作都不许直接删 `records/` 里的文件，
  要清就先 `archive()` 挪到带时间戳的 `records_archive/<时间戳>/`（随时能拿回）；
  真要删必须显式 `--purge`，并打印删了什么。`index.json` 不算棋谱、永不动它。
* 约定：测试与部署**一律不碰** `records/`；测试自己用 `tempfile` 临时目录
  （现有用例本来就是这样，已确认跑完 359 条测试后 `records/` 无新增污染）。

> 教训：**"清理一下"是最容易造成不可逆损失的操作**。凡是要动用户数据目录，
> 先备份再动；开发期的临时文件请写在临时目录里，不要用"删掉再重建"。

**后续补强（2026-10）**：上面那条"测试与部署一律不碰 records/"当时只是**约定**，
结果是 `_bench/deploy_selftest.py` 跑一次就"下"30 手并触发终局自动保存，
把几份 `0-1` 的假对局塞进了玩家的 `records/`（他又分不清哪些是自己的）。
现在改成机制保证：

* `GameState(resource_manager, record_dir=...)` 可以指定棋谱目录，
  自检脚本传 `tempfile.mkdtemp()`；
* `tools/record_safety.py` 的 `--game-dir` 口径写清楚了（要传**含 jieqi 的
  `Game` 目录**，不是项目根——传错了它会误报"0 个棋谱"，我第一次就传错了）；
* 清理动作一律"先归档到 `records_archive/<时间戳>/`，不直接删"。

### 9.5 被吃棋子条上下颠倒（用户报的）

**症状**："上方应该是对方吃的子（即我方被吃的），下方是我方吃的子
（即对方被吃的）"。

**根因**：`draw_capture_strips()` 把 `captured[theirs]` 画到了上条、
`captured[mine]` 画到了下条，正好反了。棋盘是"我方在下方"的视角，
靠近自己的那条（下面）应该摆自己吃到的战利品。

**修法**：上条 = `captured[mine]` + 标签「我方被吃」，下条 = `captured[theirs]`
+ 标签「对方被吃」；顺带给两条各加一道属于那一方的颜色（外缘色条 + 标签字色），
因为暗子图标两边都是深色，只靠图标颜色分不出是谁的损失。
回归测试：`tests/test_ui_fixes.py::TestCaptureStrips`（含"玩家执黑时同样成立"）。

### 9.6 AI 用时显示不准（用户报的）

**症状**："明明过了很久，却显示才 2000ms"。

**根因**：旧代码在搜索线程里量 `time.perf_counter()` 的差，
那是**搜索线程自己的**耗时；玩家等的还包括"线程还没被调度"和
"结果还在等主线程取走"这两段（渲染线程每帧都在抢 GIL，这部分不小）。
而且思考期间顶栏一直显示**上一手**的用时，看起来就更像"没在算"。

**修法**：计时挪到主线程——`_ai_think_start()` 在决定"该 AI 走"时开始，
`_finish_ai_think()` 在着法真正落到棋盘上时收尾；
思考期间显示**实时秒表**（`AI 思考中 3.4s`）；CPU 侧耗时留在
`_ai_think_ms_at_result` 里供对照。

**第二次反馈"到第二秒就自动重置为 0"，根因在别处**（保留记录，别再踩）：
实时秒表原本只是"取数时替换"，而 `_sync_ai_state` **每帧**都会把当前步的评估
文案写进 `gs.ai_eval_text`，`eval_for_ply(k)` 又有"这一步还没有评估就退回上一步
的"兜底逻辑。于是 AI 一想棋，顶栏立刻变回**上一步**的"AI 用时 2066ms"——
玩家看到的正是"从 0 涨到 2 秒，然后又被重置回 2000ms"。修法两条：

1. `renderer._ai_text_parts()` 在 `gs.ai_thinking` 为真时**直接返回秒表**，
   优先级高于任何评估文案（返回新列表，不去改只读字段）；
2. `_sync_ai_state()` 在思考期间**一个字都不往 `ply_evals` 里写**——
   那一刻 `ai_think_ms` 还是上一手的值，写进去既顶掉秒表，
   又会让棋谱里存一条张冠李戴的用时。

回归测试：`tests/test_ui_fixes.py::TestAiThinkTime`，其中
`test_stale_eval_text_cannot_hide_the_clock` 与
`test_sync_does_not_write_eval_while_thinking` 两条专门盯这个现象。

### 9.7 `_bench` 脚本在游戏目录里跑不起来（用户报的）

**症状**：在 `D:\py\Chinese Chess` 里执行 `python _bench/<某个脚本>.py`
直接 `ModuleNotFoundError: No module named 'jieqi'`。

**根因**：脚本头部写死 `Path(__file__).resolve().parents[1] / "stage"`，

**修法**：抽出 `_bench/_paths.py`，**向上找含 `Game/jieqi` 的那棵树**，

那个引擎已整体移除，相关探测也一并删了，见 §12。）
回归测试：`tests/test_bench_paths.py`（含"每个脚本都能 import 进去"
——这一条才抓得到 `NameError: name 'GAME' is not defined` 这种改一半的漏网）。

### 关于测试联网

`test_llm_context.py` / `test_llm.py` 都在模块级把 `urlopen` 换成了会抛异常的桩，
**测试套件绝不会真的花掉 API 额度**。这一点在开发中确实踩过：
一个用例在 `with mock.patch(...)` 块外又调了一次 `analyse()`，
结果真的发出了一次请求（日志里能看到 HTTP 401）。

实测数据（本机 Python 3.13，纯 Python 引擎）：

* normal（2 秒 / 2 采样）：开局约 **3~4 层、4 万节点**；中残局更深。
* `tests/test_tactics.py` 里「毒饵」局面：2 秒内正确拒绝吃被保护的黑卒
  （需要 2~3 层 + 静态搜索才看得到）。
* 对随机走子：**6 胜 0 负**。
* 对旧 AI：**6 胜 0 负**（旧 AI 六局都因走违规着法告负）。
* 2 秒预算下采样 1 对采样 4：**4:4**，说明这个区间采样数不是主要因素。

## 11. 后续可以再做

1. **用棋谱训练**：数据管线已经通了——`record_tool.py train --all` 直接产出
   "局面 → 实际着法 + 合法着法 + 引擎评估 + 终局胜负"的 JSONL，够训一个
   局面编码 + 策略/价值双头的小网络。建议路线：
   ① 先用**价值头**拟合 `eval_red`（学评估，容易训）；
   ② 再加**策略头**预测 `move`（注意用 `legal_moves` 做掩码）；
   ③ 最后把网络接到搜索里当叶子评估（"策略网 + 小搜索"）。
   注意：**别用 `hidden_truth` 训练**——那等于教模型偷看暗子。
2. **自对弈调参**：`EVAL_WEIGHTS` 有 8 个可调权重，`tools/selfplay.py` 与
   `_bench/ab_selfplay.py` 可以直接当适应度函数，配爬山 / 遗传算法自动调参。
3. **搜索再提速**：现在最大的开销仍是 `attack_map` + `evaluate`。可以考虑
   「增量评估」（在 make/unmake 里维护材料/威胁分），预计还能再快 1.5~2 倍，
   大约多搜一层。
4. **残局库/杀棋表**：现在靠搜索发现杀棋，深搜不够时仍会漏；可以用
   `_bench/replay_log.py` 收集"本可杀却被反杀"的局面做专项回归集。
   实测过"根节点一步杀检测"：**它其实是死代码**——`legal_filter` 已经把
   "走完自将"的着法全部过滤掉了，随机搜 4 万个三子局面都找不到一例
   "某着法会让对方一步吃将"，所以没有加进引擎。真正会漏的是**两步以上**的
   杀棋，那要靠加深搜索或做专项杀棋表。
5. **规则补充**：目前未实现「一子连续将军/长捉超过 6 回合判负」，
   只实现了 40 回合无吃子判和与三次重复判和。
6. **大模型多轮对话**：现在是把走棋记录+评估走势+上一步点评塞进单次提示词，
   如果要更省 token 或更强的连贯性，可以改成真正的多轮 `messages` 会话
   （代价是要自己管理上下文窗口与失效时机）。
